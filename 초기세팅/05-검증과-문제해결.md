# 초기세팅 검증과 문제 해결

## 완료 확인 순서

1. Node.js 22·Yarn Classic·Java 17·Gradle Wrapper가 예상 버전으로 실행된다.
2. Backend 로그의 활성 프로필과 실제 8080 포트를 확인한다. DB·브로커 등의 연결 오류를 구분한다.
3. Frontend가 localhost:5173에서 열리고 `/api/v1` 요청이 의도한 Backend로 간다.
4. 인증 우회를 끄고 발급된 계정으로 로그인한다. 필요한 메뉴와 조회 액션 권한이 있는지 확인한다.
5. 읽기용 목록을 열어 API 상태와 결과를 확인한다. 빈 결과는 필터·테스트 데이터·DB 적용 상태와 함께 판단한다.
6. 필요한 파일 작업은 준비된 테스트 원본과 저장소로 별도 확인한다. 초기 조회 확인만으로 저장·외부 발송·결제까지 검증했다고 표시하지 않는다.
7. 작업 전후 Git 변경을 확인하고 개인 .env·접속 비밀·생성물·의도하지 않은 lockfile 변경을 커밋하지 않는다.

페이지별 검증 범위는 [브라우저 검증 보고서](../references/browser-verification.md)에서 확인한다. 기존 보고서의 122개 경로 대조 결과를 새 PC의 설치 완료나 배포 환경 검증으로 재사용하지 않는다.

## 검사 명령

다음 두 블록은 각각 smartwork 저장소 루트에서 시작한다.

```bash
cd frontend
npx tsc -p tsconfig.app.json --noEmit
yarn lint
yarn test --run
yarn build
```

```bash
cd backend
./gradlew compileKotlin
./gradlew test
./gradlew build
```

실제 DB·외부 시스템을 사용하는 통합 테스트는 데이터 영향을 검토한 뒤 실행한다. 단위 테스트의 mock 성공은 DB 저장·메일 수신·PG 처리 결과를 보장하지 않는다. build·서버 기동·실제 업무 실행은 별도 확인 항목이다.

## 증상별 확인

| 증상 | 먼저 확인 | 대응 |
|---|---|---|
| node/yarn/java 명령을 찾지 못함 | 설치 셸과 PATH, WSL/Windows 실행 파일 혼용, JAVA_HOME | 같은 실행 환경의 도구를 맞추고 터미널·IDE 재시작 |
| Yarn frozen 설치 실패 | Node 22·Yarn 1.x, package.json/yarn.lock, registry·사내 CA | 버전·인증서·lockfile 변경 의도를 확인. 임의 재생성·패키지 매니저 전환으로 해결하지 않음 |
| Gradle 다운로드·컴파일 실패 | JDK 17·Gradle JVM, Wrapper 다운로드 경로, 사내 proxy/CA, backend/libs | 오류가 네트워크·컴파일·SDK 누락 중 어디인지 구분 |
| 특정 Backend 테스트가 서브모듈에서 없음 | test 필터가 다른 프로젝트에 적용되었는지 | 루트 앱만 검사할 목적이면 `./gradlew :test --tests '대상패턴'` 사용 |
| 5173/8080 포트 점유 또는 엉뚱한 응답 | 실제 포트 소유 프로세스·Vite 시작 로그·프록시 대상 | 기존 작업을 임의 종료하지 않고 사용할 프로세스와 포트를 맞춤 |
| API 연결 실패·502 | Backend 기동, VITE_API_URL 절대 URL 여부, Vite proxy | 프록시 경로·대상 포트 확인 후 Vite 재시작 |
| CORS 거부 | 브라우저 Origin의 호스트·포트와 SecurityConfig 허용 값 | 인증·API 연결 대상을 유지하며 승인된 local Origin/설정 사용 |
| 401·로그인 반복 | 인증 우회 설정, 토큰/쿠키·호스트 혼용·만료, 실제 로그인 응답 | 인증 로그·네트워크를 확인. 우회를 켜서 권한 검증 성공으로 표시하지 않음 |
| 403·메뉴 또는 버튼 없음 | 계정의 메뉴 접근·VIEW와 작업별 권한·대상 상태 | 권한 담당에게 메뉴 경로와 필요한 작업 전달. 기존 사용자 권한을 임의 변경하지 않음 |
| DB 접속 실패 | VPN·방화벽·연결 대상·계정·JDBC 설정 | DBA에게 환경·오류 코드 전달. 비밀번호는 로그/문의에 포함하지 않음 |
| 프로시저·테이블 없음 | 대상 DB·교차 DB 권한·해당 객체 적용 여부 | SQL 파일 전체 실행 대신 담당자가 객체·적용 순서 대조 |
| 조회 200이지만 빈 결과 | 기간·검색 조건·상태·담당 데이터·현행/과거 메뉴 | 합성 또는 승인된 테스트 대상 확보. 임의 고객 ID로 조회·변경하지 않음 |
| 상세는 보이지만 인감 404 | 별도 seal API의 ID·wday·파일명·storage.comseal·읽기 권한 | 상세 본문 실패와 인감 파일 부재를 구분 |
| 첨부·다운로드·양식 없음 | 저장소 루트·마운트·DB 참조·기존 파일·권한 | 파일 원본과 기능별 경로를 대조. 앱 기동과 이관 완료를 구분 |
| health가 실패하지만 일부 API는 응답 | 활성 health 구성요소와 DB·브로커·디스크 상태 | 단순 HTTP 응답을 모든 연계 정상의 증거로 사용하지 않음 |
| 내 변경이 개발 사이트에 없음 | 실행 중인 코드·배포 SHA·main 반영·workflow 결과 | 로컬 코드와 배포 코드를 구분. 확인 없이 재배포하지 않음 |

## 확인 기록에 남길 것

코드 SHA, 실행 프로필·호스트·포트, 도구 버전, 검사 명령·결과, 확인한 메뉴·API, 재현하지 못한 범위를 기록한다. 캡처에는 사용자·고객 식별값·토큰·원문 민감정보를 가린다. 문제 문의에는 민감정보 대신 마스킹한 대상과 시각·오류 코드·요청 추적 정보를 전달한다.
