## 환경과 방법

- 최초 로컬 SPA `http://127.0.0.1:5173`/API 8080, 재검증 SPA `http://127.0.0.1:3000`/API 18080, 실제 로그인 인증 활성화. 공유 개발 DB를 사용하는 로컬 프로필이다. DB 스키마 자동 변경·정기 청구·집계·RabbitMQ 소비를 비활성화하고 검증했다.
- 사용자가 지정한 [Playwright CLI 스킬](https://github.com/microsoft/playwright-cli/tree/main/skills/playwright-cli)의 설치본을 사용했다. Chromium 1440×1000, Asia/Seoul. 사용자 계정·비밀번호·브라우저 인증 상태는 증적에 포함하지 않았다.
- 메뉴·초기 입력·목록·실제 행의 상세·수정/답글 진입·등록 팝업·탭·빈 입력 오류를 검사했다. 동적 ID는 실제 화면에서 선택한 값만 사용하고 증적에서는 경로 변수로 바꿨다. 일부 등록된 대체 경로는 동일한 관찰 대상 ID로 별도 접근했고 phase로 구분했다.
- 인증된 SPA의 경로 전환으로 화면을 열었다. 직접 새로고침·새 탭 인증 유지·모든 사이드바 클릭 경로를 검증한 결과는 아니다. 화면 렌더 이후 대기 중 API를 확인했으며 `pendingRequests=0`은 화면 대조의 조건일 뿐 응답 데이터의 업무적 정확성을 보장하지 않는다.
- 로그인·토큰 갱신 외 POST/PUT/PATCH/DELETE는 브라우저에서 차단했다. 저장·삭제·업로드·반출·메일·재전송·비밀번호 초기화·원문 복호화는 실행하지 않았다. 이 방어적 차단으로 역할별 서버 거부를 검증했다고 주장하지 않는다.
- GET은 실제 개발 API를 호출했다. 공지 상세 조회수 증가, 조회 감사 기록 등 GET의 부수 효과는 발생할 수 있다. SQLCMD 조사 자체는 메타데이터 읽기 전용이었고 브라우저의 업무 조회 프로시저 호출과 구분한다.
- 실제 업무 데이터·식별자·입력값·응답 본문·토큰은 증적에 저장하지 않았다. 표 행 수는 DOM 구조 개수로 상세 정보 표도 포함하므로 실제 업무 레코드 건수로 사용하지 않는다. 기본 API 포트의 별도 디버그 실행으로 응답이 중단된 구간은 정상 근거로 사용하지 않고 검증 전용 포트에서 재확인했다. 빠른 중간 캡처보다 조회 완료 대조 결과를 우선한다.

## 비식별 화면 캡처

고객 데이터가 없는 초기 화면과 빈값 오류를 캡처하고 입력값·테이블 본문을 추가로 마스킹했다. [공지 필수 입력](../evidence/screenshots/notice-required-fields.png), [환불 업체 검색](../evidence/screenshots/refund-company-lookup.png), [가입조회 초기 화면](../evidence/screenshots/registration-initial.png). 캡처는 업무 데이터와 반영 결과를 증명하지 않는다.

## 후속 검증

업무 담당·QA: 미재현 상세의 테스트 대상과 상태를 제공하고 정상·빈 결과를 검토한다. 권한 담당: 별도 허용/거부 계정으로 메뉴·각 작업·UNMASK·파일 반출을 확인한다. 기술 담당: 격리된 데이터로 저장·삭제·금액 처리·발송·비동기·감사 기록 결과를 검증한다. 배포 담당: 실제 배포본과 메뉴 설정·다른 환경의 DB 적용을 대조한다.
